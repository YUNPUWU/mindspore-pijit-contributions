## Background

`BytecodeInliner` expands inlinable function calls into the caller and then regenerates the whole function as a single piece of bytecode. If the function has closure variables (non-empty `co_cellvars` / `co_freevars`), `STORE_DEREF` / `DELETE_DEREF` are writes to closure cells. They are **closure side effects**: such writes are visible from outside, so they must be kept and executed by the interpreter.

Originally, `EliminateClosureSideEffect` did only one thing: delete a closure write if no alive closure would read it afterwards.

## Problem

After inlining and bytecode reconstruction, nodes can appear that write a value read from a closure straight back into the same closure variable:

```
LOAD_DEREF   i
STORE_DEREF  i        # equivalent to cell_i = cell_i, no effect at all
```

Semantically it does nothing, but it was still kept as a closure side effect, leaving an avoidable write in the generated bytecode.

## Implementation

After the existing deletion logic, a second pass over the traced nodes deletes every `STORE_DEREF` that meets three conditions:

```cpp
for (auto item = traced_nodes_.begin(); item != traced_nodes_.end();) {
  if ((*item)->GetOpcode() == STORE_DEREF &&
      (*item)->getInputs()[0]->GetOpcode() == LOAD_DEREF &&            // 1. the stored value comes straight from LOAD_DEREF
      (*item)->getInputs()[0]->GetOparg() == (*item)->GetOparg() &&    // 2. the read and the write use the same closure slot
      (*item)->getInputs()[0]->GetGraph() == (*item)->GetGraph()) {    // 3. the read and the write belong to the same (sub-)graph
    item = traced_nodes_.erase(item);
  } else {
    ++item;
  }
}
```

The third condition is the easiest one to miss. The oparg of `LOAD_DEREF` / `STORE_DEREF` is an index into the cell / free variables **of its own code object**. After inlining, the same `traced_nodes_` list contains nodes from different functions, so two nodes with the same oparg do not necessarily refer to the same closure cell. Only within the same graph does an equal oparg mean the same variable.

The loop continues from the iterator returned by `erase`, so it never uses an iterator invalidated by a deletion.
